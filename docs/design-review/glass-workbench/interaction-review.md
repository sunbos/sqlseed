### 模型名称的实际裁切原因

寒蝉圆黑的 typo 与 hhea/Windows 字体度量不同。原生 input 内部编辑区域使用 normal 行高，旧设置的内部高度约 12.67px，导致 g/j/p/q/y 下降部分被裁切；输入框外框本身是正常的 40px。

共享字体声明补充 ascent 116%、descent 28.8%、line gap 0，内部区域约 19.33px，外框仍 40px；400/500 两个字重一致，字形文件及代码字体未改。样板补充实际单行输入/只读输入样例。Windows Chromium 明暗、桌面及 390px 窄屏检查完整模型名称、下降字母和重音；未用单纯 CSS 尺寸断言替代观察。

### 工作台信息架构判断

“字段规则／预览数据／关系图”作为同一工作区的并列视图有合理性，三阶段作为任务进度也有必要；两者承担不同职责。不能仅凭视觉统一宣称这是所有用户的最佳方案。依照 [WAI-ARIA Tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) 区分并列视图，参考 [GOV.UK Task list](https://design-system.service.gov.uk/components/task-list/) 对任务状态和可返回操作的处理，本轮让视图立即切换、步骤实际导航、状态来自检查证据。约 160ms 的标签反馈保留，并尊重减少动态效果设置。

已减少的重复入口：移除引导内重复 AI 区块，全局 AI 操作保留一个入口；侧栏重复“检查依赖”按钮改为状态说明；引导展开时只突出当前下一步，收起时恢复顶部计划入口。单表查看与全局检查因为作用范围不同仍然保留；这类入口应靠清楚的范围名称区分，不用增加颜色类别解释。

首次使用的主线现在是选表、检查规则、只读预览、核对写入。无选择时告诉用户从哪里开始，高级设置按需展开，返回修改不破坏工作，只有最终确认才写库。仍需用新用户验证三个问题：能否无口头指导完成首次预览；能否解释“生成表”和“仅引用表”；能否在发现规则错误后返回修改并知道何时真的写库。本轮没有开展真实用户可用性研究。
